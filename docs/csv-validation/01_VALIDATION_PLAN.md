# CSV-01 验证计划（VP）

## 1. 目的

证明 WMS / 药品 GSP 质量管理系统在批准的业务范围、技术环境和操作程序下能够持续、准确、可追溯地执行预定用途，并对药品质量、库存准确性、患者风险和 GxP 电子记录实施与风险相称的控制。

## 2. 验证对象与基线

| 对象 | 批准前必须填写的基线 |
|---|---|
| 后端 | `AllenMGu/WMS@f24952e2718f75c212f0ee1e07b79bf1df17de4f` |
| 前端 | 仓库、commit SHA、构建编号和静态文件 SHA-256 |
| 数据库 | PostgreSQL 版本、实例、Alembic `20260902_29` |
| 操作系统 | 主机名、OS/内核、补丁、时区、NTP 来源 |
| 运行组件 | Python 3.12、Web 服务、反向代理、证书、systemd 单元 |
| 身份系统 | 本地认证或 LDAP 模式、LDAP 地址、TLS 方式、Base DN；不得记录密码 |
| 配置 | 环境变量名称和值的脱敏快照、秘密版本引用 |
| 浏览器 | 批准的浏览器和最低版本 |

任何一项与执行记录不一致时必须暂停、登记偏差并评估已完成测试是否仍有效。

## 3. 范围

### 3.1 纳入

- 用户、LDAP、岗位授权、仓库授权、离职停用和职责分离；
- 合作方资质、供应商—品种授权、药品质量主数据；
- 采购订单、质量审批、收货、抽样、验收与批次库存；
- 销售订单、FEFO 分配、拣货、出库复核、发运与运输签收；
- 销后退回、不合格品、质量锁定、购进退出和监督销毁；
- 召回、召回演练、养护、近效期、批号盲盘；
- 温湿度内部数据模型、幂等、哈希链、告警和质量锁定逻辑；
- 质量风险、质量事件、CAPA、培训、受控文件和设备校准；
- 电子签名、审计追踪、打印证据、出站箱、备份、恢复、历史归档；
- 数据库升级、新建库与历史库升级路径、回退准备；
- 前端岗位可见性、关键操作入口和错误信息；
- 性能、并发、事务原子性、恢复、可用性和数据导出。

### 3.2 暂缓

- 药品追溯平台真实码制、采集、核销、上传和对账；
- 实际温湿度网关、探头、外部告警渠道和断网补传；
- 九州通正式协议、适配器、联调和生产对账。

暂缓仅表示当前版本不启用外部能力，不得把相关测试标记为“通过”。启用前必须发起变更并完成专项验证。

### 3.3 不纳入

- 通用办公终端本身的验证；
- 外部服务商系统内部控制；
- 未经批准的旧 WMS 无批号接口作为药品正式账务入口。

## 4. 风险方法

严重度 S、发生概率 P、可检测性 D 采用 1–5 分，初始 RPN=`S×P×D`。

| RPN | 等级 | 要求 |
|---|---|---|
| 1–19 | 低 | 文件审查或基础测试；记录理由 |
| 20–49 | 中 | 至少一条正向和一条负向测试 |
| 50–79 | 高 | 独立复核、边界/失败/恢复测试，放行前关闭风险 |
| 80–125 | 极高 | 未完成缓解和验证前不得上线 |

任何患者、药品质量、批次可追溯、未授权放行、电子签名或审计完整性风险，即使 RPN 较低，也按关键功能管理。

## 5. 验证策略

| 活动 | 目的 | 主要证据 |
|---|---|---|
| 设计审查 | 确认需求可测试、设计能控制风险 | URS、FS/DS、RA、评审记录 |
| 代码与迁移审查 | 确认实现和数据库变更受控 | PR、commit、CI、Alembic check |
| IQ | 确认批准组件和配置正确安装 | 命令输出、版本、配置、服务状态 |
| OQ | 证明功能和控制在正常/异常/边界条件下有效 | API/UI/SQL/日志/审计证据 |
| PQ | 证明真实岗位和代表性数据可完成端到端流程 | 业务记录、签名、批次库存、报表 |
| 迁移验证 | 证明数据完整、准确、可读、可追溯 | 源包哈希、映射、数量与抽样 |
| 恢复演练 | 证明备份可用和恢复后一致 | 备份哈希、恢复日志、RTO/RPO、复核 |

自动化测试可支持 OQ，但只有在测试版本、输入、输出、环境和审查均受控时才作为证据。人工可用性和岗位操作仍须执行。

## 6. 角色与职责

| 角色 | 职责 |
|---|---|
| 系统所有者 | 提供资源、确认预定用途、接受运行责任 |
| 流程所有者 | 编制 URS/PQ、提供代表性数据、确认业务结果 |
| 质量负责人 | 批准计划/风险/方案/偏差/VSR/放行 |
| 验证负责人 | 维护计划、RTM、执行状态和证据索引 |
| IT/开发 | 提供设计、构建、部署、技术测试和缺陷修复 |
| 数据负责人 | 批准映射、核对迁移数量和关键字段 |
| 执行人 | 按批准步骤执行并实时记录实际结果 |
| 独立复核人 | 核对步骤、证据、偏差和结论；不得复核自己的执行 |

## 7. 前置条件

- URS、风险评估、FS/DS 和测试方案已批准；
- 测试环境与生产等效性已评估；
- 测试人员已培训且权限符合矩阵；
- 测试数据已批准并脱敏；
- 时钟同步、审计、日志和证据目录可用；
- 代码与数据库基线冻结；
- 回退方案和备份已经准备并校验。

## 8. 总体接受标准

1. 所有关键 URS 在 RTM 中有设计、风险和已通过测试证据。
2. IQ 关键项 100% 通过；OQ/PQ 关键测试 100% 通过。
3. 无未关闭的严重/高风险偏差；中风险偏差有批准的处置和残余风险接受。
4. 权限、电子签名、审计追踪、备份恢复、迁移和并发库存专项通过。
5. 自动化回归、Ruff、编译、Alembic 升级/current/check 和健康检查通过。
6. SOP、培训、支持、监控、备份、恢复和业务连续性措施生效。
7. 质量负责人签署 VSR 和上线放行；任何系统显示的“成功”不能替代该审批。

## 9. 偏差和停止规则

出现以下情况必须暂停相关测试：基线不符、关键步骤缺证据、审计不可用、系统时间异常、测试账号职责冲突、数据被非预期修改、严重安全问题或可能影响生产数据。恢复前必须登记偏差、评估影响、批准处置并从适当步骤重新执行。
